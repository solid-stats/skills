# Research: Best-practice architecture for a deterministic Rust parser shipped as both a CLI and a long-running queue worker, 2024–2026. Context: an OCAP (JSON-based game replay) parser that must produce bit-for-bit deterministic output, versioned via an explicit parser contract (output schema + version), consumed by a TypeScript backend over RabbitMQ. Verify against current practice: (1) crate layout — single crate with multiple bins vs a cargo workspace with core/cli/worker crates — for parser-type projects; (2) error-handling layering: thiserror for library errors + anyhow at the binary edge — current consensus and when alternatives (snafu, miette) win; (3) how deterministic output is engineered and tested in real Rust parsers/serializers — ordered maps (BTreeMap/IndexMap), float formatting, canonical JSON, golden/snapshot tests (insta); (4) cross-language output-contract versioning between a Rust producer and a TypeScript consumer — schema files (JSON Schema), semver discipline, compatibility/contract tests; (5) fuzz and property testing policy for parsers (cargo-fuzz, proptest, arbitrary) plus coverage tooling (cargo-llvm-cov) — what a rigorous policy looks like; (6) Rust queue-worker patterns (lapin or amqprs: graceful shutdown, concurrency caps, ack discipline). For each: actual current practice with sources, and what to adjust.

## Summary
For a deterministic Rust OCAP parser shipped as CLI + queue worker, the defensible architecture uses a Cargo workspace (core/cli/worker crates) with thiserror in the library crate and anyhow at binary edges — this is the current community consensus. Deterministic output requires BTreeMap for ordered serialization and explicit float formatting; IndexMap's default serde gives no ordering guarantee, so serde_seq or BTreeMap is mandatory for canonical JSON output. Insta with sorted redactions is the right snapshot-testing tool for non-deterministic collections. Lapin is the recommended AMQP client: it is runtime-agnostic (tokio default), supports basic_qos prefetch for concurrency throttling, and provides automatic connection recovery via enable_auto_recover(). Coverage visualization via cargo-fuzz helps identify untested code paths and optimize fuzzing seeds, but specific tooling flags and workflow steps had claims refuted during verification and should be confirmed against current cargo-fuzz documentation.

## Findings

### 🟡 Cargo workspace with separate core/cli/worker crates is the standard layout for parser projects shipping multiple binaries. The core crate exposes the deterministic parser as a library; cli and worker crates are thin binary wrappers that add error-handling context at the edge.
_Confidence: medium_

No directly confirmed claim covered crate layout. This reflects community consensus and the logical separation required by the thiserror/anyhow layering pattern, but no primary-source quote was verified for this sub-question specifically. Treat as medium confidence.

### 🟡 Error handling: use thiserror for typed, structured errors in the core library crate, and anyhow at the binary boundary (CLI and worker main functions) for rich context. This is the current Rust community consensus for the library-vs-application error handling split.
_Confidence: medium_

This sub-question had no claims that survived the adjudication process; the layering pattern is well-established community practice but was not independently verified against primary sources in this research run. Confidence is medium, not high.

### 🟢 IndexMap's default serde implementation provides no guarantee that serialization formats will preserve key-value pair ordering. For canonical/deterministic JSON output, use BTreeMap (insertion-ordered by key sort) or serialize IndexMap via serde_seq (as a sequence of tuples). Never rely on IndexMap's default serde output for bit-for-bit determinism.
_Confidence: high_

Official IndexMap docs state explicitly: 'The default serde implementation serializes IndexMap as a normal map, but there is no guarantee that serialization formats will preserve the order of the key-value pairs.' The serde_seq module exists specifically to address this gap. Note: the stronger claim that serde_seq 'explicitly addresses deterministic ordering' was refuted — serde_seq serializes as tuples but its determinism guarantee was not confirmed by verified quote.

Sources: <https://docs.rs/indexmap/1.6.2/indexmap/serde_seq/index.html>

### 🟢 Insta supports sorted redactions via a selector to handle HashSet and other collections with non-deterministic serialization order, making snapshot tests stable across runs without requiring BTreeMap everywhere.
_Confidence: high_

Official insta.rs docs: 'A special feature of the redaction support is the ability to sort a map or sequence at a selector. This is particularly useful if you're working with a HashSet or something similar that has non deterministic serialization order but you need to assert on it.' Note: a companion claim about general redaction support was refuted on entailment grounds; the specific sorted-redaction feature for non-deterministic collections is confirmed.

Sources: <https://insta.rs/>

### 🟢 Lapin is the correct AMQP client for a Rust queue worker. It is runtime-agnostic — the same code works with tokio (default), smol, or async-global-executor via feature flags. Use basic_qos(prefetch_count, options) on the channel to limit unacknowledged message delivery and throttle consumer concurrency. Enable automatic connection + topology recovery via ConnectionProperties::default().enable_auto_recover(), then call channel.wait_for_recovery(error).await on recoverable errors.
_Confidence: high_

All three lapin claims were confirmed from the primary source (official README + source code). Runtime-agnostic design confirmed via feature flags in Cargo.toml. basic_qos docs: 'Set the quality of service for this channel. Limits the number of unacknowledged messages that the server will deliver.' Auto-recovery: README explicitly documents enable_auto_recover() and wait_for_recovery(error).await. Note: prefetch_count controls delivery backpressure, not task-level concurrency — application-level semaphores are still needed for true concurrency caps. The graceful Channel::close() pattern was refuted on entailment grounds and should be verified separately against current lapin API docs.

Sources: <https://github.com/amqp-rs/lapin>

### 🟡 Coverage visualization for fuzzing helps identify which code paths are being reached and which are not, allowing corpus and fuzz target optimization. The cargo-fuzz book explicitly recommends this workflow. However, specific tooling flags (-Cinstrument-coverage, cargo fuzz coverage command behavior) and claims about mutation-based vs generation-based fuzzing superiority were all refuted during verification — do not rely on memorized workflow steps; consult current cargo-fuzz documentation.
_Confidence: medium_

Confirmed: 'Visualizing code coverage helps you understand which code paths are being fuzzed and — more importantly — which aren't. To help the fuzzer exercise new code paths, you can look at what it is failing to reach and then either add new seed inputs to the corpus, or tweak the fuzz target.' Refuted: the specific compiler flag claim (-Cinstrument-coverage), the cargo fuzz coverage command workflow description, the llvm-tools-preview recommendation, and the mutation-vs-generation superiority claim were all refuted. Use cargo-fuzz book directly for current workflow.

Sources: <https://rust-fuzz.github.io/book/cargo-fuzz/coverage.html>

### 🔴 Cross-language output contract versioning (Rust producer → TypeScript consumer over RabbitMQ) was not covered by any verified claim in this research run. Standard practice is: define a JSON Schema as the contract artifact, apply semver discipline to schema versions, and run contract tests (e.g., Pact or schema-validation integration tests) at the consumer boundary. These recommendations reflect community practice but carry low confidence as no primary sources were verified.
_Confidence: low_

## Caveats
Several sub-questions had all claims refuted or no claims submitted: (1) Crate layout (workspace vs single crate) — no primary source verified; consensus recommendation is based on architectural reasoning, not confirmed quotes. (2) thiserror + anyhow layering — no claim survived; this is common practice but unverified here. (3) Graceful lapin shutdown — Channel::close() claim was refuted on entailment; consult current lapin API docs for the correct close pattern. (4) cargo-fuzz coverage tooling details — all specific workflow claims (compiler flags, command behavior, llvm-tools-preview) were refuted; the cargo-fuzz book is the authoritative source and should be read directly. (5) Cross-language contract versioning — entirely unverified. (6) IndexMap serde_seq determinism — the stronger claim was refuted; serde_seq avoids map-format ambiguity but its determinism guarantee depends on key ordering in the source structure. (7) The lapin basic_qos confidence is medium rather than high because 'consumer-side concurrency throttling' conflates delivery backpressure with task-level concurrency — application semaphores are required for true concurrency caps.
